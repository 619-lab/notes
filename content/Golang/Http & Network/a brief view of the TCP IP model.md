## 互联网是如何运作的？
* 因特网实际上是一个分布在世界各地并连接不同设备的网络。即使你看不到物理线，你也可以想象你的智能手机通过虚拟线连接到一个WiFi路由器上，虚拟线可以让你和千里之外的数据服务器进行交互。   
* 当你想要通过互联网将数据发送到与你设备相连的设备时，需要遵守一些规则。所有在互联网上传输的数据都是由0和1组成的二进制数据。   

   * 首先，用于发送数据的应用程序需要与设备上的硬件进行通信进而通过互联网发送数据。此外，设备的硬件需要像路由器一样与互联网上实际传输数据的设备进行通信。
   * 当你寄信给朋友时，你需要在信封标上收信人的地址，这样这封信就会送到正确的人手里。类似地，通过因特网发送数据时，你需要知道最终将接收数据的设备地址。
   * 当一个网络应用程序在设备中启动来传输或接收数据时，它将在像8080这样地端口号上进行帧听数据。发送方需要知道接收方设备的端口号，以便被正确地应用程序接收到数据，而不是其他无关的应用程序。这些端口号是由操作系统随机分配，但我们可以强制操作系统将应用程序绑定到某个端口号上。
   * 接收数据的设备需要对过来的数据有个预先的认识，知道它在看什么，否则设备将无法理解这些过来地数据。数据可以是图像、歌曲、纯文本消息或者 html 文档。因此，我们需要告诉接收方数据类型，以便它能够正确地解释它。
* 上面四个步骤描述了因特网上数据传输地通信模型。每个步骤都有协议定义，根据协议地类型，这些步骤中的每一步都对数据进行相应地格式化，以接收方能够正确的提取数据。

## TCP/IP 通信模型
* TCP（Transmission Control Protocol） 传输层协议，IP（Internet Protocol）为网络层协议。
* 这些协议一起驱动了大多数互联网间的通信。此刻，你的浏览器正在使用 TCP/IP 模型从服务器加载本网页。
	* 应用层: BGP DHCP DNS FTP HTTP HTTPS IMAP LADP MGCP MQTT NNTP NTP POP ONC/RPC RTP RTSP SMTP SNMP SSH Telnet TLS/SSL XMPP...
	* 传输层: TCP UDP DCCP SCTP RSVP ...
	* 网络层： IPv4/6 ICMP OCMPv6 ECN IGMP IPsec...
	* 链路层: ARP NDP OSPF Tunnels(L2TP) PPP MAC(Ethernet Wi-Fi DSL ISDN FDDI)...
	
*  MAC（Media Access Control）地址是设备制造商提供的硬件的唯一地址。使用 MAC 地址，两个设备之间的通信成为可能。

## HTTP 协议
HTTP 协议基于 TCP/IP 或 UDP/TP。在数据发送到接收方之前，发送方与接收方之间的通信通道需要被打开。

*  TCP的三次握手
	* 首先，客户端使用 TCP 协议将 SYN(synchronize)flag 置为1像服务端发送一个空数据包不包含任何应用数据。当服务器接收到这个包时，它知道客户机正在尝试建立连接。
	* 服务端返回一个空数据包并将SYN 和 ACK标志置为1。当客户端收到这个包时，它知道服务器已经响应并愿意接受请求。
	* 然后客户端发送一个空数据包并将 ACK（acknowledge）标志到1，等服务端收到此包，一个 TCP 通信通道已经打开，连接正式建立。

* 一旦建立连接，HTTP 协议数据将作为应用程序数据发送到网络包中的服务器。数据包含纯文本格式的 HTTP head 显然这个数据会被编码至二进制。服务端收到数据后，会返回包含响应头和 html 文档纯文本 当服务端发送回所有数据后1+，客户端需要发送一个空包将 ACK 置为1进行确认收到。
* 服务器没有更多的数据发送的时候，它会发送一个空数据包，并将 FIN（finished）标志设置为1，以表示完成消息。接着客户端可以确认这个包并关闭连接。
* 在HTTP 长连接（HTTP persistent connection） keep-alive，相同的 TCP 连接将用于请求其他资源，这样效率更高，因此我们不必一次又一次地进行相同的 TCP 三次握手。很多时候，客户端和服务端的通信没有那么顺畅。可能会丢失数据包，数据包可能以错误的顺序到达，因此需要重新传输这些数据包。这边 UDP 就表现得很不同了，在 UDP 协议中，接收方不需要发送接收包 对包的丢失和包顺序也不会作任何处理。
* 安全问题， HTTP是一种不安全的协议，因为HTTP协议中的数据是以纯文本格式编码的。任何中间人都可以监听TCP通信并读取通过web传输的个人数据。


## SSL/TLS 概述
HTTPS代表超文本传输协议安全（HyperText Transfer Protocol Secure），但它在某些方面具有误导性。HTTPS协议不能单独做数据加密，实际上它依赖于SSL或TLS协议层。

* HTTP协议层和TLS协议层都是应用层的一部分。TLS层的作用是使用TLS握手(在TCP握手之后)与服务器建立安全连接，并使用与服务器协商的一些加密算法加密HTTP数据。最终的加密数据成为服务器将要接收的网络数据包的应用数据。由于应用程序数据是加密的，任何中间人都可能获得数据，但无法理解它。这阻止了中路进攻。
* 当HTTP协议与TLS协议结合使用时，称为HTTPS协议。为了调用浏览器或程序来使用TLS进行通信，我们通常在URL中使用https://协议前缀。
* 在 tcp 连接建立后，TLS 握手开始。
	* 首先，客户端会发送一个包含 TLS 协议层的空包到服务端，这个协议层会包含一些元数据和一个 Client Hello 的消息，并附加了目前支持的密码套件列表。 
	* 除了一个密码套件列表外，我们还将发送一个服务器名称指示(SNI)消息，该消息指出我们试图连接的服务的主机名(域名)。服务器使用此命令返回与此主机名匹配的适当SSL证书。
	* 当服务器收到客户端Hello包时，它用一个包含服务器Hello消息的空包进行响应。这个包包含服务器从客户机提供的选项列表中选择的密码套件。然后它发送一个包，其中包含我们要求使用SNI值的域名的SSL证书。此时，服务器已经没有什么要发送的了， 因此它发送带有服务器Hello Done消息的包。
	* 客户端一旦收到SSL证书，我们的应用程序就可以对其进行验证。此证书还包含服务器选择的密码套件的公钥。密码套件包含一列加密算法和一个散列函数，用于加密和验证客户机和服务器之间传输的数据。
		* 如果服务器选择上述密码套件，则意味着服务器将使用RSA算法对批量数据加密的共享密钥进行加密。客户机和服务器使用的批量加密算法是AES 256位(CBC模式)。
		* 密码套件的最后一部分是创建数字签名的单向哈希函数
		* 一旦客户端和服务器就密码套件达成一致，就可以启动加密通信。到目前为止，我们所有的数据包都没有加密，因为它们不包含任何应用数据，也没有加密的先验知识。
		* 客户机现在生成用于批量数据加密的共享密钥。如密码组中所述，它将创建AES对称密钥算法的256位密钥。这个密钥需要与服务器共享。
		* 使用从SSL证书获得的服务器的RSA公钥，客户机将对共享密钥进行加密，并将其与消息客户机密钥交换一起发送到服务器。
		* 此包还包含更改密码规范消息，表明客户端正在使用商定的密码规范进行数据加密。
		* 在同一个包中，客户端发送一个完成的握手消息来表明来自客户端的TLS握手已经完成。此消息使用共享对称密钥(AES)加密。
		* 一旦服务器接收到这个包，它将通过使用其私钥解密数据来接收共享的对称密钥。因为没有其他人可以访问私钥，所以这个共享密钥不能在网络上读取
		* 通过查看更改密码规范消息，服务器也会将其数据读写模式更改为约定的密码规范，然后使用刚刚提取的共享密钥对握手消息进行解密。
* 由于握手消息已经完成，它将向客户机发送一个包，其中包含一个更改密码规范消息，以表明服务器正在使用商定的密码规范进行数据加密，以及一个使用共享密钥加密的完成消息。	一旦客户端接收到这个数据包，TLS 握手就完成了，应用程序数据可以通过使用选定的批量数据加密算法加密解密通过TCP通道传输。


## TLS的数据完整性
当服务器发送回数据时，它不仅发送加密的数据副本，还发送一个数字签名。数字签名是通过使用私钥加密数据生成的。   
在使用数据之前，客户端可以使用服务器的公钥验证这个数字签名，如果失败，TCP连接将被删除。    
 
* 这就是与服务器协商的单向哈希函数发挥作用的地方。服务器首先使用hash函数(如SHA)计算数据的哈希值，然后使用私钥对其加密(签名)。其结果是每个人都在谈论的数字签名，它也被称为消息认证代码或MAC。

* 当客户端接收到加密的有效负载时，它使用对称密钥算法恢复数据和数字签名。然后，它首先检查数字签名是否真的由服务器使用服务器的公钥签名，然后提取散列值。
* 然后，客户端通过对从服务器接收的数据使用相同的散列函数计算自己的散列。如果服务器发送的散列与它自己计算的散列匹配，则数据是安全的。
